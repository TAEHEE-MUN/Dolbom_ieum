현재 단계: 기획·시험 설계. 실제 구현과 성능 검증 완료를 뜻하지 않음.

1. 목표와 핵심
────────────────────────────────────────
“활동지원사는 방문을 쉽게 기록하고, 기관은 확인할 기록과 그 이유를 쉽게 찾는다.”
장애인활동지원 전자바우처를 보완하는 방문 기록·검토 플랫폼이다.
이용자에게 추가 인증을 요구하지 않고, 지원사의 시작·휴게·복귀·종료 기록과
위치·시간 정보를 분석해 기관의 기록 대조와 설명 확인을 돕는다.
위치·휴대폰 움직임만으로 실제 돌봄, 두 사람의 동행, 부정수급을 확정하지 않는다.
결제·급여 산정·환수·자동 제재·정부 연동은 이번 핵심 화면 범위 밖이다.
인터뷰 근거는 기관 사무국장 1명이다. 두 학생의 메모를 두 명의 인터뷰로 세지 않는다.

2. 사용자와 권한
────────────────────────────────────────
활동지원사: 고령 사용자를 고려한 앱. 본인 일정·기록·요청만 확인한다.
기관 관리자: PC 웹. 직원/이용자 등록, 일정 배정, 질문, 정정 승인, 기관 답변을 처리한다.
장애인 이용자: 앱 설치·QR·생체인증·휴게 승인 등 조작 역할 없음.
여러 기관이 사용하지만 지원사는 동시에 한 기관 소속이다. 다른 기관 기록은 볼 수 없다.
플랫폼 운영자용 별도 콘솔은 이번 웹 디자인 범위 밖이다.

3. UX 방향
────────────────────────────────────────
앱: ‘누구의 방문인가 / 현재 상태는 무엇인가 / 다음에 무엇을 누르는가’를 먼저 보여준다.
황색 포인트 + 진한 글자. 색만으로 상태를 구분하지 않고 문구·아이콘을 함께 사용한다.
황색 사용만으로 색각 접근성이 해결되는 것은 아니다. 대비와 실제 가독성을 검토한다.
큰 글씨·큰 버튼·짧은 선택형 입력. 지도 해석과 긴 글쓰기를 필수로 하지 않는다.
웹: 지도보다 확인할 업무 목록이 먼저. 점수보다 이유·구간·품질·다음 행동을 제시한다.
방문 종료, 휴대폰 저장, 서버 전송, 기관 검토 완료는 서로 다른 상태다.
‘기기 저장 완료’를 ‘기관 전달 완료’로 표현하지 않는다.

4. 서비스 흐름과 화면 연결
────────────────────────────────────────
첫 이용: M01 가입 → M02 안내 → M03 기관 연결 → M04 오늘 방문.
기관 준비: A03 지원사/이용자 등록 → A04 일정 배정 → M04에 일정 수신.
정상 방문: M04 → M05 시작 전 → M07 돌봄 중 → M08 휴게 → M07 복귀 → M10 종료 → M11 요약.
예시 통일: 김지원 지원사 / 이용자 가 / 방문 09:00~13:30 / 휴게 11:00~11:30.
결과: 전체 4시간30분, 휴게30분, 돌봄 기록4시간. 결제 인정 시간이라는 뜻은 아니다.
휴게는 실제 버튼 시각으로 기록. 자동 30분 차감·자동 복귀하지 않는다.
임시 방문: M04 → M06 등록 이용자 선택 → 시작 → M07. 기관 A05에는 ‘임시’ 표시.
확인 사건: A02 후보 → A06 근거 → A07 질문 → M14/M15 답변 → A07 기관 답변 → 검토 완료.
정정: M12/M13 원본·요청 값·사유 → A08 승인/반려 → 앱 결과 표시.
정상 방문 전체에 답변을 요구하지 않는다. 관리자가 질문한 사건에 답변을 제출한다.

5. 데이터 흐름 — 디자이너가 알아야 할 상태 변화
────────────────────────────────────────
① 기관 웹 배정 → 서버 권한 확인 → 기관별 일정 저장 → 해당 지원사 앱에 수신.
② 앱 버튼 → 기기 저장 성공 → 화면 상태 변경 → 전송 대기 → 서버 전송.
③ 돌봄 중 허용된 위치·시각·정확도 기록. 움직임 센서는 별도 시험 기능.
④ 서버 권한 확인·중복 제거·원본 저장 → 앱에 수신 확인 → 전송 완료 표시.
⑤ 시간 규칙 / 위치 품질 점검 / 유효 구간 패턴 / 과거 패턴 AI로 분석.
⑥ 관리자에게 후보와 근거 → 질문 → 지원사 답변 → 기관 답변·검토 결과 저장.
⑦ 정정 승인 시 새 버전 생성 → 관련 분석 재평가. 원본은 덮어쓰지 않는다.
휴게·종료 때 위치와 앱의 움직임 수집 요청을 중단한다. 이전 자료의 전송은 이후에도 가능.
인터넷이 없어도 시간은 기기에 기록. 위치는 실제 측정 성공한 자료만 저장한다.
오프라인에는 기관이 새 기록을 볼 수 없으므로 ‘마지막 수신 시각’을 표시한다.
기록 발생 시각과 서버 수신 시각을 구분한다. 센서 누락은 ‘정지’가 아니다.
온라인 관리자 표시 목표: 조건 충족 후 2~5분. 아직 실측 전이며 항상 실시간을 보장하지 않는다.

6. 분석 항목과 표시 방식
────────────────────────────────────────
거주지 밖: 위치 맥락. 밖이라는 이유 하나로 부정 사건을 만들지 않는다.
거주지 밖 2시간: 장기 외출 확인 후보. 병원 동행 등 정상 예외 존재.
같은 구역 3시간: GPS 체류 후보. 재가 돌봄이면 정상 가능.
과거 패턴 차이: 비교 가능한 자료가 있을 때 AI 후보. 부족하면 ‘분석 준비 중’.
추가 A 시간 중복 / B 방문 사이 이동 시간 불일치 / C 반복 짧은 이탈 /
D 시작·종료만 거주지 근처 / E 예정 대비 기록 시간 차이: 모두 포함.
추가 F 반복 정정: 운영·교육 개선 목록. 부정 점수에서 제외.
움직임 미관측 2시간: 센서 시험 항목. GPS 체류3시간과 별개다.
폰을 놓고 정상 돌봄을 하는 경우와 놓고 외출한 경우를 센서만으로 구분하지 못한다.
표시 출처: 규칙 / AI 후보 / 센서 시험 / 데이터 품질 / 운영 개선.
같은 원인의 후보는 묶는다. 검증되지 않은 ‘부정 확률95%’ 같은 수치는 넣지 않는다.

7. 디자이너에게 필요한 결과물
────────────────────────────────────────
앱 기본17프레임(M12 목록/상세 분리) + 상태 변형, 웹10개 설계 단위 + 패널/상태 변형.
각 프레임에 ID·목적·구성요소·주 버튼·다음 화면·예외 상태 주석을 남긴다.
프로토타입5개: 정상 방문 / 오프라인 종료 / 임시 방문 / 질문·답변 / 정정 승인.
공통 요소: 일정 카드, 버튼, 상태 배지, 시간 입력, 저장·전송 안내, 질문 카드, 확인창.
예시 인물·시간·합계는 앱과 웹에서 동일하게 유지한다.
기존 PDF·이미지는 과거 시안이다. 최신 정책은 이 전달본과 기획 텍스트를 따른다.

8. 미정·시험 항목
────────────────────────────────────────
가입 인증 수단, 기관 연결 코드 세부 방식, 관리자 초대는 미정/제안.
동시 방문 차단, 임시 방문 사후 확인, 기관 이동·장기 미응답 처리도 추가 결정 필요.
지원사 답변 전에 오탐 사건을 닫는 운영 방법은 미정. 현 정책상 완료는 쌍방 답변 필요.
보관 기간, 센서 권한 문구, 탐지 반경·임계값·재알림은 검증 후 확정.
미정 항목은 주석을 남기고 자동 승인·자동 종결을 임의로 확정하지 않는다.
