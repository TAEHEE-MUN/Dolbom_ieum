1. 현재 판정
기본 와이어프레임 작업은 진행 가능. 모든 운영 예외가 확정된 개발 최종 명세는 아님.
정상 방문, 휴게/복귀, 오프라인 종료, 기관별 권한, 정정 승인, 쌍방 답변 조건은 연결됨.

2. 발견 항목
V01 [문구 오류 보완 가능] M07이 전송 오류에도 ‘위치 신호를 기다림’으로 안내한다.

  측정 문제: “시간은 기록 중이에요. 위치를 확인하지 못했어요.”
  권한 거부: “위치 권한이 없어 시간만 기록해요.”
  휴게: “쉬는 중에는 위치를 기록하지 않아요.” 각각 구분한다.

  기관 질문은 M15, 내가 보낸 정정/일정 요청은 M13 요청 상세·결과 변형으로 연결해야 한다.
V03 [정의 필요] 화면상 돌봄 경과 시간은 휴게 제외 누적시간. 전체 방문 경과시간과 구분한다.
  휴게 중 종료도 허용하고, 자정 넘김과 여러 번의 휴게를 합산하는 테스트 추가 필요.
V04 [자료 노출 결정] ‘등록 이용자’ 범위가 기관 전체인지 담당 지정 이용자인지 미정.
  임시 방문을 위해 모든 이용자 주소를 내려받는 것을 기본값으로 삼지 않는다.
V05 [가입 정책 미정] 기관 최초 개설, 관리자 초대/인증, 지원사 연결 방법이 제안 단계다.
  도용 등록·다른 기관 기록 노출을 막는 서버 검증 설계 필요.
V06 [운영 결정] 한 앱 동시 방문 차단 여부, 임시 방문 사후 확인·반려 절차 미정.
  일정 변경은 실제 기록을 바꾸지 않도록 현재 구분 유지.
V07 [미응답 운영] 모든 확인 사건은 쌍방 답변 필수이므로 관리자가 오탐을 발견해도
  자동 종결할 수 없다. 후보와 정식 확인 사건을 구분할지 사용자의 결정이 필요하다.
  현재 정책 아래에서는 시간 경과나 통화만으로 답변·검토 완료 처리하지 않는다.
V08 [운영 결정] 기관 이동 시 미전송/진행 방문/미응답 사건 처리와 과거 기록 접근 미정.
V09 [환경 예외] 강제 종료·전원 꺼짐·저장 공간 부족·기기 변경·위치 권한 중도 철회 시
  수집 지속을 보장하지 않는다. 마지막 저장·수신 시각과 데이터 공백을 표시해야 한다.
  앱 삭제를 앱이 가로채서 막을 수 있다고 가정하지 않는다.
V10 [시각 검증 전] 큰 글씨 확대, 황색 대비, 버튼 간격, 화면 읽기 순서, 로딩/비활성 버튼
  이유와 저장 실패 안내는 실제 디자인에서 검증해야 한다.

3. AI를 만들기 위해 필요한 자료
필수 A: 어떤 상황을 ‘확인 필요’로 볼지 기관과 합의한 시나리오.
  정상: 재가 지원 3시간, 병원 동행 2시간, 장보기, 정상 휴게.
  품질 문제: GPS 미수신, 통신 지연, 절전 중단, 기기 시각 불일치.
  확인 후보: 일정과 설명으로 해소되지 않은 시간/장소 차이. 확정 부정사례와 구분.
필수 B: 수집 가능한 시험 자료 범위.
  동의 받은 테스트 인원·일수·기종, 정상 활동 시간표와 관찰 기록, 실제/가상 구분.
  GPS만 보고 실제 행위를 정답으로 만들지 않는다.
필수 C: 기존 활동 시간·기록·정정/소명 양식과 기관 실무자의 판단 사례.
  개인정보를 제거한 형식부터 검토. 실제 운영 자료 접근 권한이 있다고 가정하지 않음.
필수 D: 데이터 사전.
  기관/방문 ID, 관측 시각, 서버 수신 시각, 좌표 정확도, 활동/휴게 구간,
  일정 유형, 등록 주소 버전, 현장 사유, 전송/수집 상태, 비교 기준 버전.
  가속도 등 추가 센서 수집은 확정하지 않음. 배터리·권한·필요성을 먼저 검토.
필수 E: 검증 계획.
  방문/날짜 단위로 학습·검증·시험 분리. 같은 방문의 인접 좌표를 무작위 분할하지 않음.
  미래 방문의 성과를 검증할 때 과거 시점까지의 자료만 기준으로 사용.
  유효 자료가 충분한 대상의 성능과 자료 부족으로 분석 못 한 비율을 함께 보고.
  오탐/누락, 방문당 알림 수, 관리자 검토 시간, 탐지 지연을 측정.
  가상 자료 성능은 실제 현장 성능과 구분. 관리자 답변은 자동으로 부정 여부 정답이 되지 않음.

4. 권장 AI 시제품 구조 [제안]
시간 기록 → 규칙 점검. 위치 부재여도 가능한 항목은 검사.
위치 기록 → 품질 통과 구간 → 거주지 거리/체류/외출 시간 → 통계 기준과 AI 후보 비교.
처음에는 중앙값·평소 변동 범위 기준을 만들고, 충분한 자료에서 Isolation Forest 등
비지도 이상치 탐지 모델이 실제로 추가 도움이 되는지 비교한다. 모델은 아직 선정하지 않음.
LLM에 전체 GPS 경로를 보내는 방식을 기본으로 두지 않는다. 설명은 근거값으로 만들 수 있다.
모델 점수는 이상 정도이며 ‘부정수급 확률’이 아니다. 희귀한 정상 외출도 이상치가 될 수 있다.
기관 간 운영 자료를 자동 합쳐 학습하지 않는다. 공통 테스트 모델과 기관별 비교 기준을 구분한다.
휴대폰 미소지·다른 사람이 소지한 경우를 GPS만으로 판별할 수 없다는 범위 제한 유지.

5. 배터리 저사용 설계 [개발 제안, 수치 미확정]
기본 원칙: 시간 기록을 위해 백그라운드 타이머를 계속 돌리지 않는다.
  시작·휴게·복귀·종료 시각을 저장하고 화면 복귀 때 경과시간을 계산한다.
  기기 시계 변경/재부팅은 별도 검증. 앱 정지 중 실제 돌봄은 확인할 수 없음.
위치 수집: 시작/복귀는 사용자가 화면에서 실행. 돌봄 중에만 OS 위치 서비스를 사용.
  이동 상태와 필요한 정확도에 따라 갱신을 조절한다. 요청 간격은 실제 수신 보장이 아니다.
전송: 로컬 저장 후 묶음 전송. 지도는 사용자가 열 때만 표시하고 불필요한 반복 통신을 줄인다.
휴게/종료: 위치 요청 중단 + 늦게 도착한 콜백의 구간 검사. 휴게에 측정된 좌표는 저장하지 않음.
  휴게 전에 측정됐으나 늦게 배달된 자료는 발생 시각 기준으로 처리.
서버: AI 분석은 우선 서버에서 수행. 오프라인에서 서버 분석·푸시 즉시 전달은 불가.
측정 실패: 짧은 간격의 고정밀 재시도 무한 반복 금지. 제한 후 품질 안내.

Android: 사용자 시작 버튼을 누르는 화면에서 위치 유형의 foreground service를 시작하는
방안 검토. 필요한 서비스 선언·런타임 위치 권한·알림을 갖춰야 하며 단순 백그라운드 작업과
같다고 생각하면 안 된다. 시작 상황·OS 버전에 따라 제한이 다르다.
iOS: Core Location의 백그라운드 설정·사용 목적 안내·적절한 권한 흐름을 구성한다.
무조건 ‘항상 허용’부터 요구하지 않고, 사용자 시작형 세션에 필요한 권한 수준을 선택한다.
Flutter/React Native 등 공통 UI를 선택해도 이 동작은 OS별 구현·시험이 필요하다.

핵심 상충관계
  짧은 수집 간격 ↔ 배터리와 저장량 증가.
  묶음 전송 ↔ 관리자 알림 지연.
  낮은 정확도 ↔ 집/인접 건물 구분 어려움.
  정지 시 갱신 감소 ↔ 장기 체류 판단에 쓸 증거 감소.
  새 좌표가 안 온 이유가 절전/누락일 수 있으므로 ‘3시간 같은 곳’으로 추정하지 않는다.
따라서 지도 경로가 촘촘해 보이는 것보다 확인 목적에 필요한 정확도·지연부터 합의한다.

6. 실기기 시험 준비
  iPhone 및 Android 실제 기종/OS/배터리 상태, 맥 개발환경·개발 프레임워크 확인.
  4시간 또는 실제 근무 길이 기준으로 동일 경로·밝기·통신조건에서 비교.
  A: 위치 기능 끔 / B: 고정 간격 수집 / C: 상태별 간격+묶음 전송.
  충전 여부·초기 잔량·다른 앱 사용·절전모드·온도도 기록. 조건을 맞춰 반복.
  지표: 배터리 감소 퍼센트포인트, OS 전력 측정 자료, 유효 좌표 비율, 관측 공백,
        거주지 이탈 시점 오차, 알림 지연, 중복/누락, 휴게·종료 후 위치 미수집.
  배터리가 적게 닳아도 대부분 수집 실패했다면 성공으로 보지 않는다.
  목표치는 사용자 수용성과 기종별 기준값을 확보한 뒤 합의한다.

7. 사용자에게 요청할 정보
Q1 실제 앱 개발 기술·서버 기술·담당 인력·개발 경험. 미정이면 가능한 언어.
Q2 사용 가능한 Android/iPhone 기종·OS, 맥 보유 여부.
Q3 시험 자료: 실제 기관 자료 접근 가능 여부 / 동의한 학생의 모의 방문 / 모두 미확보.
   테스트 인원·가능 일수와 실제 현장 판단을 도울 관리자 유무.
Q4 탐지 우선순위 1~2개: 거주지 밖, 3시간 체류, 2시간 외출, 과거 패턴 차이.
Q5 필요한 지도 수준: 거주지 안/밖 및 체류 중심 vs 실제 이동 길 재현 중심.
Q6 통신 가능 시 허용할 알림 지연: 수십 초 / 수분 / 방문 종료 후.
Q7 하루 사용시간과 허용 가능한 추가 배터리 소모. 미정이면 먼저 기준 측정.
Q8 일정·소명 등 개인정보 제거 양식, 앱 개발·시연 마감, 월 서버/도구 예산.
추가 운영 결정: 후보의 사건 승격 시점, 임시 방문 검색 범위, 무응답 처리.
알림 수신자는 관리자만으로 확정. 아래 8~11절은 위 질문에 대한 후속 답변을 반영한다.

8. 개발 기술 선정안
  앱: Flutter(Dart)로 Android/iOS 공통 화면과 방문 상태·로컬 저장을 구현.
  위치: Android Kotlin / iOS Swift의 네이티브 위치 서비스를 Flutter와 연결.
  Python FastAPI: 방문 이벤트 수신·기관 권한 검증·분석·알림/답변 API.
  관리자 웹: FastAPI + Jinja2 기반 HTML/CSS/JavaScript. 초기부터 별도 프런트엔드 서버를
  운영하지 않는 소규모 시험 구성. 화면 복잡도가 커지면 프런트엔드 분리를 재검토한다.
  SQLite: 기기 로컬 기록과 시험 서버 저장에 사용하되 두 DB는 별개.
  Python 표준 도구/NumPy·pandas로 합성 자료 생성, scikit-learn으로 통계/모델 비교.
  현재는 같은 네트워크의 개발 PC에서 서버와 웹 실행. 서버 PC가 꺼지면 수신 중단.
  기기에 ‘localhost’를 서버 주소로 넣지 않는다. 실제 운영 데이터 없이 가상 자료로 접속 시험.
  관리자 알림은 먼저 웹 알림함에서 구현. 외부 푸시·배포·지도 API 비용은 별도 범위.
  지도 없이도 가상 기준점 대비 거리·시간줄·구간도를 사용해 탐지 논리를 검증할 수 있다.
  Flutter 자체가 배터리 절감을 보장하지 않음. OS 위치 요청·전송·실기기 결과로 검증.

9. 합성 데이터 시험 설계
  AI에는 시나리오와 생성 코드를 만들게 하고, 좌표·시각은 제약조건을 둔 Python 코드로 생성한다.
  임의 문장이나 숫자 목록을 그대로 학습 자료로 쓰지 않는다. seed·생성 버전·시나리오 ID 저장.
  별도 보관: 가상 실제 활동 경로(정답) / GPS 오차·누락을 넣은 관측 로그(모델 입력).
  실제 기관/이용자 집 주소를 넣지 않고 가상 기준 좌표를 사용한다.
  예시 묶음: 재가 체류, 외출 후 복귀, 병원 장기 동행, 반복 외출, 시간 중복, GPS 튐,
  통신 지연, 권한 없는 시간 기록, 휴게 중단. 정상/확인후보/품질불량을 구분한다.
  동일 원본 경로의 조금 다른 복제본이 학습·시험 양쪽에 들어가지 않게 시나리오 단위로 분리.
  2시간 경계값으로 생성한 정답을 같은 규칙으로 맞힌 결과는 규칙 시험일 뿐 AI 성능 증거가 아님.
  과거 패턴 모델은 다른 생성 조건·정상 예외·미래 시점의 별도 시험 묶음으로 평가.
  합성 데이터 결과로 실제 부정수급 탐지율·현장 정확도를 주장하지 않는다.
  배터리와 화면 잠금 중 GPS 수집은 본인 동의 하에 실제 휴대폰에서 별도 시험해야 한다.

10. 추가 패턴 — A~F 모두 기획 범위로 확정 (구현·성능 검증 전)
  A 시간 중복: 같은 지원사의 실제 방문 구간 중복. 원래 명세에 이미 포함된 규칙.
    오프라인 다중 기기·승인 정정 후에도 검사. 예정 일정 충돌과 구분.
  B 이동 시간 불일치: 앞 방문 종료와 다음 시작 사이에 이동하기 어려운 거리.
    충분한 위치·시각 품질과 이동수단 고려. GPS 튐은 품질 문제로 먼저 분리.
  C 반복적 짧은 이탈: 같은 방문 중 거주지 반경 밖으로 여러 번 나갔다 들어옴.
    누적 외출과 횟수로 확인. 경계 GPS 흔들림·산책·심부름은 정상 가능.
  D 시작·종료만 거주지 근처: 양 끝은 거주지 근처이나 중간 유효 관측 대부분이 외부.
    병원 동행 등 정상 외출과 비교. 2시간 외출 사건과 중복 알림 통합.
  E 일정 대비 기록 시간 차이: 예정보다 지나치게 짧거나 길며 설명이 없는 방문.
    일정 변경·정정·휴게 반영 후 검사. 법정/청구 인정 시간을 자동 판단하는 기능 아님.
  F 반복 정정 패턴: 같은 유형의 시작/종료 정정 요청이 반복.
    교육·앱 오류 개선 신호가 우선이며 부정수급 점수로 사용하지 않는다.
  G GPS 급격한 튐/수집 중단: 위치 신뢰성·복구 대상. 행동 이상과 별도 품질 목록.
  A~F 모두 적용한다. G는 기존 데이터 품질 관리로 유지한다.
  각 패턴에 정상 외출·정정·오류 사례를 포함해 오탐을 시험한다. 세부 임계값은 시험 후 결정.

11. 체류 관측과 알림 지연·전력 실험
  체류의 ‘세밀함’은 휴대폰이 같은 구역에 있었는지에 관한 유효 관측과 관측 공백 파악이다.
  실내 몇 미터 이동·지원사의 신체 동작·휴대폰 소지 여부를 GPS로 입증하는 설계는 제외.
  모든 시험 모드에서 휴게·종료는 즉시 위치 요청 중단.
  실험 제안: 이동 중 30~60초 요청 / 체류 중 1~3분 요청 / 2~5분 묶음 전송.
  위 숫자는 초기 비교용 제안이며 OS가 그 주기로 전달한다는 보장도 사용자 확정도 아니다.
  단기 고정밀 확인이 유효 관측을 늘리는지, 정지 중 요청이 전력만 늘리는지도 따로 비교한다.
  위치 정확도 부족 상태가 오래가면 고정밀을 계속 강제하지 않고 판단을 보류한다.
  ‘2시간 외출’의 2시간은 패턴 조건. 알림 지연은 조건이 충족된 시각부터 기관에 표시될 때까지.
  예: 14:00에 조건 충족 → 14:03에 웹에 표시되면 지연 3분.
  통신 가능 상태에서 조건 충족 후 관리자 화면 표시까지 2~5분 목표로 확정.
  수집·전송·분석·화면 갱신 전체 지연을 측정한다. 전송만 5분 기다려 목표를 초과하지 않게 설계.
  OS 지연·품질 부족으로 판단 불가하면 별도 품질 상태로 표시한다. 오프라인은 연결 복구 후 평가.
  배터리 목표는 숫자를 임의 확정하지 않고 동일 조건 4시간 기록 켬/끔/최적화 비교 후 결정.
  단말 모델·OS·배터리 상태·밝기·통신·화면 사용을 기록. 방전량과 분석 가능한 구간 비율을 함께 보고.

13. 추가 확정 사항 및 휴대폰 움직임 시험 설계 (2026-11-19)
────────────────────────────────────────
범위 확정
  A 시간 중복 / B 방문 간 이동 시간 불일치 / C 반복적 짧은 이탈 /
  D 시작·종료만 거주지 근처 / E 일정 대비 기록 시간 차이 / F 반복 정정 패턴을 모두 포함.
  A·B·E는 규칙 기반, C·D는 위치 구간 패턴 기반으로 먼저 구현한다.
  F는 교육·기록 품질 개선 지표다. AI 부정 점수나 자동 제재에 사용하지 않는다.
  GPS 튐·누락은 별도 품질 항목. 같은 원인의 알림은 묶고, 사유와 개별 근거를 보존한다.
  과거 패턴 AI는 비교 가능한 방문 데이터가 충분한 경우에만 검토 후보를 생성한다.

새 실험 M2: 휴대폰 움직임 미관측 2시간
  사용자 가설: 휴대폰을 두고 외출한 상황을 알아내고 싶음.
  한계: 휴대폰을 놓고 정상 돌봄을 하는 경우에도 동일한 기록이 나온다.
  GPS의 같은 구역 3시간 체류(R2)와 다른 항목이며 두 기준은 각각 유지한다.
  GPS로 휴대폰의 실내 미세 움직임을 판별하지 않는다. 움직임 센서를 별도 시험한다.
  2시간은 검증 전 시험값. 연속 유효 관측 조건·민감도는 실기기 실험 후 결정한다.
  센서 미지원·권한 거부·OS 중단·수집 공백은 ‘판단 불가’이지 ‘움직임 없음’이 아니다.
  앱 미사용·화면 꺼짐도 휴대폰 정지의 증거로 사용하지 않는다.
  다른 사람이 폰을 움직이는 경우도 있으므로 움직임 있음 역시 지원사 현장 존재의 증거가 아니다.

수집 및 데이터 흐름 제안
  서비스 시작 → 위치 및 동의한 움직임 기능 가동 → 기기에서 구간별 요약 → 로컬 저장 → 전송.
  서버: 기관·방문 연결 확인 → 품질 점검 → 규칙·패턴 분석 → 관리자 확인 목록.
  휴게·종료 즉시 위치 및 앱의 움직임 수집 요청 중단. 휴게 공백을 연속 정지로 합산하지 않는다.
  원시 센서를 계속 서버로 보내지 않고 움직임 있음/없음/판단 불가, 구간 시작·끝,
  관측 범위·수집 상태·기기 시각·서버 수신 시각·방문 ID를 우선 기록한다.
  기기 내 요약 주기와 센서 방식은 아직 제안이며, 누락과 저전력 실험 후 확정한다.
  Android 연속 센서는 백그라운드 제약이 있어 foreground service 등 적절한 방식을 시험한다.
  iOS Core Motion 활동 분류는 기기 움직임 정보다. 미세 움직임 감지·지속 전달을 보장하지 않는다.
  플랫폼별 실험 결과가 불충분하면 M2는 판단 보류하고 위치·시간 기본 기능은 유지한다.

화면 추가 명세
  M02 안내: 움직임 시험 목적, 수집 시간, 중단 시점, 기관 열람 범위와 선택 권한 설명.
  M07/M16: 위치 기록 상태와 움직임 기능 상태를 구분. 권한 미허용 시 시간 기록 유지.
  A02/A06: 위치 체류와 기기 움직임 항목을 별도 표기. 데이터 품질·대상 구간·판단 한계 표시.
  시험 알림: ‘휴대폰 움직임이 장시간 관측되지 않았습니다. 현장 상황 확인이 필요합니다.’
  ‘지원사 외출 확인’, ‘부정수급 확정’, 임의 확률은 표시하지 않는다.
  관리자만 최초 확인 → 필요시 지원사 설명 요청 → 지원사 답변·기관 답변 → 검토 완료.
  F는 운영 개선 목록으로 분리. 설명 요청 전에는 지원사에게 자동 답변 의무를 부여하지 않는다.

온라인 알림 목표 및 실제 시험
  조건 충족 후 관리자 표시까지 2~5분 목표. 수집·전송·서버 처리·화면 갱신을 모두 포함.
  통신 가능해도 OS 수집 지연은 발생할 수 있어 목표 달성률과 지연 분포를 실측한다.
  과거 기록 동기화로 발견한 사건은 발생 시각과 발견 시각을 구분한다.
  실기기 시험 가능 확정. 참여 동의를 받고 시험하며 실제 수급자의 정보는 사용하지 않는다.
  시험 1: 휴대폰을 놓고 현장에 머무르는 정상 돌봄 역할.
  시험 2: 동일하게 휴대폰을 놓고 시험 참여자가 자리를 비우는 역할.
  시험 3: 휴대폰을 소지하고 실내 이동 / 다른 참여자가 폰만 움직임.
  시험 4: 화면 잠금·절전·권한 거부·강제 종료·통신 끊김·휴게·종료.
  시험 1과 2는 기기 신호가 같을 수 있으며, 이를 구분 못하는 한계를 결과에 그대로 기록한다.
  관찰자가 실제 상황·시각을 따로 기록. 합성 데이터 정답을 실기기 성능 근거로 사용하지 않는다.
  같은 기기에서 기록 끔 / 위치만 / 위치+움직임 최적화를 같은 시간·환경으로 비교한다.
  지표: 배터리 감소량, 유효 관측 비율, 정상 돌봄 확인 알림 빈도, 알림 지연, 중단 후 수집 여부.
  Android·iPhone 각 실제 모델/OS, 참여 인원, 시험 시간은 다음 실험 준비 때 확인한다.
