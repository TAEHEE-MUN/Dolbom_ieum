동행이음 | 앱·웹 프론트 기준 백엔드 정합성 검토
작성일: 2026-11-23

1. 결론과 적용 범위
앱 20개, 관리자 웹 11개 정적 화면의 상태·입력·출력을 기존 API 및 DB와 비교했습니다.
화면별 조회 API, 관리자 이메일 로그인, 검토 보류 처리, 요청 입력 검증을 추가했습니다.
기존 지원사 앱의 문자 인증 정책은 유지합니다.
정적 Figma 데모를 실제 서버 데이터 모드로 전환한 것은 아닙니다.
정적 UI는 재현용으로 유지되며, 이번 변경은 실제 연동에 필요한 서버 계약과 처리 규칙입니다.
기존 main.dart 앱과 FastAPI 관리자 화면은 기존 연동 코드가 있는 별도 진입점입니다.

2. 활동지원사 앱 기능
정적 화면: 로그인/회원가입 안내, 오늘 방문, 예정 방문, 돌봄, 휴게, 사유,
종료 확인/결과, 일정 변경, 요청 대기, 정정, 기록 목록, 기관 요청,
답변/완료, 보낸 요청, 내 정보, 기록 상세 2종.
실제 기능 코드: 문자 인증, 기관 연결 수락, 배정 이용자·일정 확인,
시작→휴게→복귀→종료, 휴게 제외 시간 계산, SQLite 기록과 재전송,
위치 동의·권한이 없으면 시간만 기록, 휴게·종료 시 위치 구독 해제,
현장 사유·정정·일정 변경 요청·기관 질문 답변.
새 API: /api/screens/mobile-home, /visits, /schedule, /requests, /cases/{id}.
기관 소속 전에는 모바일 홈 API가 403을 반환하며 기존 bootstrap으로 등록 상태를 확인합니다.
미완료: 새 정적 화면과 VisitStore 연결, 실제 SMS 발송 설정, 실물 기기 백그라운드/배터리 시험.

3. 관리자 웹 기능
정적 화면: 로그인, 현황, 일정, 방문, 검토, 변경 요청, 지원사·이용자,
기록 품질, 기관 설정, 사건 상세, 정정 비교.
관리자 인증: POST /auth/admin/login {email,password}.
Supabase 비밀번호 로그인 후 활성 기관 관리자 소속까지 확인합니다.
기관 미등록/지원사 계정에는 관리자 세션 쿠키를 발급하지 않습니다.
HTTPS에서는 Secure, HttpOnly, SameSite 쿠키를 사용하며 쓰기에는 CSRF 검사가 있습니다.
운영자 등록: Supabase Auth에서 이메일 계정을 만든 뒤 private.provision_agency_email 사용.
일반 사용자에게 운영자 등록 함수 실행 권한은 없습니다.
화면별 조회: /api/screens/overview, /visits, /cases, /cases/{id}, /requests,
/corrections/{id}, /schedule, /people, /quality, /settings.
정적 웹 5175는 실제 로그인하지 않습니다. 기존 연동 웹 8001은 이메일 로그인을 사용합니다.

4. 화면과 API 대응
현황: 한국시간 날짜, 방문 4개 상태, 미시작 일정, 검토 상태, 대기 요청 수.
방문: 원본 이벤트/시간과 승인 정정 적용 이벤트/시간을 모두 제공.
방문 필터: 날짜, 지원사, 이용자, 상태, 임시 여부, offset/limit.
검토 목록: 출처·상태 필터. 지원사에게 관리자 미요청 후보는 RLS로 숨김.
사건 상세: 이유·근거·시간·현장 사유·질문/답변·정정·관리자 감사 기록.
변경 요청: 일정 변경과 실제 기록 정정을 별도로 제공.
정정 비교: 원본 이벤트, 제안 값, 승인 반영 요약을 분리.
사람: 소속 지원사 검색, 등록 이용자, 담당 이용자 배정 목록.
품질: 위치 미수신, GPS 정확도 부족, 진행 중 수신 지연을 구분.
기기 현재 상태/권한 상태는 직접 보고가 없으므로 추정하지 않음.
설정: 기관·관리자·규칙 버전 조회. 편집/보관정책 미확정 항목은 명시적 미구현 값.

5. 쓰기 명령 계약
POST /api/command {action,payload}; 실제 역할과 기관 범위는 DB RPC에서 재확인합니다.
profile / accept_invitation: 프로필, 기관 연결 수락.
invite / recipient / recipient_update / assign: 지원사 연결, 이용자·주소, 배정.
schedule / schedule_update: 일정 등록·관리자 변경.
schedule_request / decide_schedule: 지원사 변경 요청·기관 승인/반려.
sync: 시작·휴게·복귀·종료 이벤트와 위치 묶음 업로드.
note: 선택적 현장 사유.
correction / decide: 원본 보존 정정 요청·승인/반려.
question / answer: 관리자 요청·지원사 답변.
review: 추가 확인 필요. 기관 답변은 저장하지만 사건은 agency_pending 유지.
close: explained(설명 확인) 또는 corrected(정정 확인).
지원사 답변·기관 답변·결과·미처리 정정 해소가 필요하며 오래된 version은 거부합니다.
질문/답변/검토/수정 등은 최신 version을 전달합니다.
날짜는 타임존이 있는 ISO 문자열을 사용합니다. 화면 표시는 Asia/Seoul입니다.
정정 요청의 범위 문자열은 서버에 그대로 보내지 않습니다.
현재 실제 기록 정정은 event_id와 proposed.occurred_at을 지정하는 단일 시각 단위입니다.
일정 변경은 proposed.starts_at과 ends_at입니다.
휴게 삭제·대상 이용자 변경 정정은 별도 정책/DB 구현 전까지 실제 승인 대상으로 제공하면 안 됩니다.

6. AI·데이터 처리
수집 → 원본 보관 → 승인 정정 적용 조회 → 품질 확인 → 시간 규칙/경로 후보 → 관리자 검토.
기존 규칙: 2시간 거주지 밖, 3시간 유사 위치, 반복 외출, 시작·종료만 거주지,
시간 중복, 이동 시간 불일치, 예정 시간 차이, 종료 미수신, 반복 정정.
과거 자료가 조건을 만족하면 기록 시간 기반 IsolationForest 후보를 추가합니다.
신규: 돌봄 구간 GPS 수집 공백은 품질 항목으로 표시하고 휴게 공백은 제외.
위치 미수신은 장시간 미움직임으로 판정하지 않습니다.
휴대폰 움직임 센서 2시간 탐지는 센서 수집이 아직 없어 구현되지 않았습니다.
GPS 체류와 휴대폰 움직임 센서는 다르며 동행·부정수급 확정 근거가 아닙니다.
기존 연동 웹에는 화면이 열려 있을 때 2분 간격 분석 호출이 있습니다.
서버 상시 스케줄러·푸시 알림은 없습니다. 새 정적 웹에서도 분석을 호출하지 않습니다.
따라서 현재 2~5분 자동 통지는 운영 보장이 아니라 미검증 목표입니다.

7. DB 변경
신규 테이블은 없습니다. 기존 15개 테이블과 RLS를 유지합니다.
private.command에 review와 재전송 ID 내용 충돌 검사를 추가했습니다.
운영자 전용 이메일 관리자 등록 함수를 추가했습니다.
기존 DB 업그레이드 SQL: db/frontend_alignment.sql.
새 빈 DB 초기화용 schema.sql, setup_all.sql도 같은 규칙으로 맞췄습니다.
기존 DB에 setup_all.sql을 재실행하면 안 됩니다.
원격 반영: 미완료. 직접 MCP는 OAuth token refresh failed,
다른 연결은 permission 오류를 반환했습니다. 원격 DB를 변경하지 않았습니다.
로컬 PostgreSQL 호환 테스트에서 업그레이드가 원본 이벤트를 보존함을 확인했습니다.

8. 검증 결과
Python: 27개 테스트 통과.
Flutter analyze: 문제 없음. Flutter 전체 테스트 6개 통과.
앱: 20개 화면, 좁은 폭·큰 글자·스크롤, 휴게 제외 계산, 정정·답변 흐름 확인.
정적 관리자 웹: 11개 화면, PC/모바일, 로컬 에셋, 필터/검색/등록/검토/정정 통과.
기존 연동 웹: 이메일 로그인 UI, 모의 데이터 현황/상세/메뉴/작은 화면 통과.
DB: 기관 격리, RPC 역할, 후보 비공개, 원본 불변, 재전송, 양측 답변,
정정 승인·사건 재검토, 오래된 버전 차단, 추가 확인 보류, 운영자 등록 권한 통과.
실제 Supabase 사용자 세션·SMS·실시간 DB 왕복은 인증 연결 오류로 미검증입니다.
AI 실제 정확도·오탐률과 배터리 절감률은 측정하지 않았습니다.

9. 다음 연결 단계와 남은 차이
가. Supabase MCP 재인증 후 frontend_alignment.sql 적용 및 원격 권한 재검증.
나. 관리자 이메일 시험 계정 등록, 앱 SMS 제공업체 설정.
다. 정적 프론트 모델을 실제 API/VisitStore로 연결. 정적 시연 모드는 별도로 유지.
라. 담당 관리자별 세부 승인 권한은 현재 admin/worker 2역할보다 세분화가 필요.
마. 담당자 배정, 권한 변경 요청, 보관·삭제 정책은 화면만으로 실제 정책을 확정하지 않음.
바. 휴게 삭제·대상 이용자 정정과 한 번에 여러 시각 정정 정책을 확정 후 추가.
사. 센서 수집·기기 상태 보고·서버 분석 작업·푸시 및 실기기 시험.
현재 상태를 운영 가능한 통합 완성본으로 보아서는 안 됩니다.
